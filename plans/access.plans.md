# Доступы и безопасность

Решения пользователя 2026-11-19. Правила обязательные: проверяются и в работе панели, и при
разработке (тестами), а не только договорённостью.

## 1. Каждый видит и меняет только своё

**Админ** (`admin.*`) управляет и техникой, и содержимым:
- учётные записи, роли, привязка карточек, публикация по сайтам;
- **схема карточки специалиста**: админ сам добавляет и правит свойства карточки (новое поле,
  справочник, порядок) — как свойства инфоблока в Битриксе, без программиста;
- у каждого свойства отмечено, может ли его менять врач и нужно ли подтверждение менеджера.

**Врач** (`doctor.*`) — только свои данные:
- видит и правит **только свою** карточку и **только поля, которые админ разрешил врачу**;
- в техническую часть (учётки, роли, схема карточки, публикация, чужие данные) доступа нет;
- **ассистент** — только слоты и записи своих врачей.

Как обеспечиваем:
- **В работе:** права проверяются на сервере (политики Laravel) — для каждого действия и для
  каждого поля; скрытая кнопка в интерфейсе защитой не считается.
- **При разработке:** код раздела `app/Doctor` обращается к данным только через сервисы `app/Domain`,
  которые сами ограничивают «свою запись» и «разрешённые поля»; прямых запросов к таблицам из
  раздела нет. Тесты: врач не может прочитать или изменить чужую карточку, запрещённое поле,
  технические разделы; разделы не обращаются к коду друг друга.
- Все изменения — в журнал (кто, когда, было → стало).

## Роли (макет «Пользователи и роли», 2026-11-19)

Роли заданы в коде (так права проверяются тестами), новая роль — через разработчика:
**админ**, **менеджер**, **учебная часть** — раздел `admin.*`; **врач**, **ассистент** — `doctor.*`.
С 2026-11-20 ещё две роли в `admin.*`, каждая видит только своё: **«Партнёр FD»** — курсы, где FD указан
партнёром; предлагает пункты программы через подтверждение учебной части; курсантов и документов не видит;
**«SMM»** — публичные фото курсов (без `lab/` и скрытых), скачивание архивом.
Учётки заводит админ, самостоятельной регистрации нет. Врач привязан к одной карточке, ассистент — к
одному или нескольким врачам. Свою роль менять нельзя, последнего админа нельзя понизить или заблокировать
(как в Task CRM). «Закрыть доступ» не удаляет: карточка, правки и журнал остаются. Матрица прав «раздел ×
роль» — в макете `mockups/pages/admin-users.html`, вкладка «Роли и права»; она же — основа тестов прав.

## Журнал (макет 2026-11-19)

Журнал только дописывается: изменить или удалить запись не может никто, включая админа. Пишутся изменения
(кто, объект, «было → стало»), обмен с сайтами и каждый запрос API, входы, неудачные входы и отказы в доступе
(403: врач открыл чужую карточку, у ключа сайта нет права). Личные данные слушателей и пациентов в «было →
стало» не пишутся — только факт изменения. Срок хранения — решить.

## 2. API — самое закрытое место

API видит **только данные для обмена**; списки участников, документы слушателей, учётные записи,
журналы и всё остальное для него закрыты.

Три уровня защиты:
1. **База данных.** Контейнер `api` подключается к базе **отдельным пользователем MySQL** с правами
   только на таблицы/представления обмена (`exchange_*`: опубликованные специалисты, курсы и
   запуски, клиники, свободные слоты) и на запись заявок на приём. Остальные таблицы для этого
   пользователя не существуют — даже ошибка в коде API не откроет их.
2. **Приложение.** У каждого сайта свой ключ с правами (например, RF — только чтение специалистов
   и курсов); отдаётся только то, что опубликовано на этом сайте.
3. **Сеть.** `api.*` только по HTTPS, только с IP наших серверов, ограничение частоты; каждый запрос —
   в журнал.

Контейнеры `admin` и `doctor` работают под своими пользователями базы; у `doctor` права уже, чем у `admin`.

## Открыто

- Кабинет слушателя на сайте ИХС (макет «Мои курсы») показывает его курсы и удостоверения. Если
  эти данные идут из панели, API нужен узкий доступ «данные одного человека по его ID», а не
  списки участников. Решить при проектировании слушателей и документов.
