# API панели — обмен с сайтами

Схема согласована с пользователем 2026-11-19. Клиент на стороне сайтов — модуль Битрикса
`gmr.ecosystem` (facts 2026-10-27), по одному на каждом сайте.

## Общая схема

**Истина — в панели, сайты — витрины.** Данные идут в две стороны.

```
                ┌──────────────── ПАНЕЛЬ ИХС (одна база) ───────────────┐
                │  admin.*      doctor.*       api.*                    │
                │  админы,      врачи,         вход для сайтов          │
                │  менеджеры    ассистенты     (у каждого свой ключ)    │
                └───────────────────────────────▲───────┬───────────────┘
                                                │       │
                  сайт спрашивает и присылает   │       │  сайт забирает изменения
                  (слоты, запись на приём)      │       ▼
                ┌───────────────┬───────────────┴───┬───────────────────┐
                │  сайт ИХС     │   сайт FD         │   сайт RF         │
                │  gmr.ecosystem — модуль-«почтальон» на каждом сайте   │
                └───────────────┴───────────────────┴───────────────────┘
```

## 1. Панель → сайты: публикация

Специалисты, курсы и запуски, клиники.

- `gmr.ecosystem` раз в несколько минут спрашивает: «что изменилось с прошлого раза?» (`since`).
- Панель отдаёт только изменения и только то, что публикуется на этом сайте.
- Сайт обновляет у себя карточки (контент-менеджеру правка закрыта).
- Ночью — полная сверка на случай потерь.

Пример: врач поменял фото → менеджер подтвердил → через пару минут фото на ИХС и FD, на RF — нет
(там врач не публикуется).

## 2. Сайт → панель: действия посетителя

Запись на приём — в реальном времени:

```
Пациент на сайте          Сайт (gmr.ecosystem)         Панель
  открыл запись    ──►  «свободные слоты врача X?» ──►  отдаёт слоты по клиникам
  выбрал время     ──►  «занять слот, имя, тел.»   ──►  занимает слот атомарно:
                                                        ок / «уже занято»
  видит «заявка
  отправлена»      ◄──  ответ                      ◄──  запись со статусом
  (параллельно сайт шлёт заявку на почту колл-центра — как сейчас)
  в кабинете на сайте: статус   ◄── статус ◄────────── ассистент / менеджер
```

Если панель недоступна: сайт принимает заявку как «перезвоните мне» (почта колл-центра уходит как
обычно) и досылает в панель позже; специалисты на сайте показываются из последней копии.

## 3. Защита

- Отдельный адрес `api.*`, только HTTPS, запросы только с IP наших серверов.
- У каждого сайта свой ключ и свои права (например, RF читает специалистов, но не записывает на приём).
- Каждый запрос — в журнал.
- Записи на приём содержат имя и телефон — это передача ПДн между юрлицами; идёт по договорам
  поручения (у юриста, facts 2026-11-17).

## 4. Адреса (черновик)

JSON, версия в адресе (`/v1/`), чтобы менять API, не ломая старые сайты.

| Запрос | Кто | Зачем |
|---|---|---|
| `GET /v1/specialists?since=…` | все сайты | изменения в специалистах |
| `GET /v1/courses?since=…` | все сайты | курсы и запуски |
| `GET /v1/clinics` | ИХС | клиники |
| (в `courses`) | все сайты | галерея запуска: ссылки на опубликованные фото из Selectel (2026-11-20) |
| `GET /v1/slots?doctor=…&from=…` | ИХС | свободное время сейчас |
| `POST /v1/appointments` | ИХС | занять слот и создать заявку |
| `GET /v1/appointments/{id}` | ИХС | статус для кабинета пациента |

## Открыто

- Сайты забирают изменения сами (по расписанию) или панель ещё и «толкает» уведомление об изменении —
  начинаем с первого, второе добавим при необходимости.
- Формат общего ID специалиста и как он попадает в инфоблок на сайтах.
